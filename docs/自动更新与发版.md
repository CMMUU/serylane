# 自动更新与版本同步

## 每次发版的固定完成标准

此流程适用于本次及后续所有 Serylane 发版，除非用户明确缩小范围：

1. 审核变更、版本号、发布说明和官网相关文案，完成前端、原生及发布同步脚本测试。
2. 将已审查代码推送 GitHub；使用 trusted main 的 `Release bundles` 与 `publish_current=true`，六平台及安装检查通过后才创建不可变版本标签并公开 Release。
3. 同步 Gitee 对应仓库的分支、标签和 Release 附件。所有安装包、签名、校验文件验证通过后，最后发布更新清单及 `downloads.json`；只重试幂等读取，不放宽完整性校验。
4. 使用既有官网流水线同步受影响的功能说明、测试并部署 trusted main，然后回验线上构建与六个平台的最新下载路由。
5. 对照 GitHub/Gitee 的代码引用、版本、附件大小与 SHA-256、更新清单及官网返回值。任何镜像或官网步骤失败、跳过或仍在进行，都不报告整个版本已完成；修复后幂等重跑。

Gitee 默认保留最新一个正式版附件，历史代码、标签、发布记录及 GitHub 历史安装包保持原样。真实电脑登录、重启及本机安装单独验收，发布成功不代表已替换本机应用。

## 显式兼容发布

默认稳定发行必须配置完整 Apple 签名与公证凭据。维护者明确选择先交付非 TUN 功能时，可从 trusted main 手动执行 `Release bundles`，同时设置 `publish_current=true`、`compatibility_release=true`，并保持 `release_tag` 为空。其他分支、tag push、旧标签修复或未请求公开发行的组合均不接受此选项。

仅在 Apple 凭据全部缺席时使用临时签名兼容包；部分凭据直接失败，完整凭据仍走 Developer ID 与公证验证，不在失败后降级。更新签名、六平台安装包完整性和 macOS TUN 身份校验不变。发布说明及官网必须写明未公证和 macOS TUN 未就绪，兼容发布不作为 TUN 修复验收。

## 日常使用

设置 → 软件更新。推荐“自动（国内优先）”渠道：选择可用渠道中的最高稳定版，同版本优先 Gitee；Gitee 不可用或尚未同步新版时使用 GitHub。下载失败只会回退到版本、大小、摘要和签名都相同的另一渠道，不替换为旧版或不同安装包。需要固定来源时选择 Gitee 或 GitHub 并保存更新偏好。已明确指定的单一来源不会被覆盖。更新偏好独立保存，不更改代理、端口或登录启动设置。

开启自动检查后，启动延迟 18 秒检查，之后每 6 小时检查一次。自动下载是独立的可选项；安装不是后台自动操作。下载成功后仍需点击“安装并重启”并确认连接中断提醒。下载缓存在内存中，退出会丢弃，不支持断点续传。

## 发版者配置

1. 在 GitHub 仓库的 Actions Secrets 中配置 `TAURI_SIGNING_PRIVATE_KEY`（私钥文件内容），可选 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`。同步 Gitee 使用现有的 `GITEE_TOKEN`。
2. 公钥固定在 `src-tauri/tauri.conf.json`。私钥必须在仓库外安全备份，不能提交、上传为 Release 附件或粘贴到对话中。丢失密钥会让现有安装无法信任后续版本；轮换需单独规划。
3. `npm run version:set -- 0.7.1` 同时更新 package.json、package-lock 两个字段、Cargo.toml、Cargo.lock 及 tauri.conf.json。`npm run version:check` 检查全部字段；`node scripts/version.mjs --tag v0.7.1` 同时校验标签。
4. 完成测试、审核发布说明并提交全部相关文件。只在明确授权发版后推送匹配的稳定标签。CI 缺少签名密钥、版本不一致或任一平台格式检查、Clippy、测试或构建失败时不发布。0.7.0 在检查阶段停止发版，其已同步标签保持不变，首次正式发布使用 0.7.1。
5. CI 构建六个平台，再验证每个更新包的 Minisign 文件签名和认证注释，生成 `latest.json`（GitHub 地址）、`latest-gitee.json`（Gitee 地址）及 `SHA256SUMS.txt`，完整验证 GitHub 附件后才公开 Release。
6. Gitee 同步严格使用这些原始文件，不重新构建或重新签名。安装包和签名全部上传并验证摘要后，最后上传两个更新清单。镜像未完成时会暂时不可用，应用自动模式可以继续使用另一个可用渠道。

代码或标签推送只同步分支和标签。经维护者确认，Gitee 仅保留最新 1 个正式版的镜像附件，GitHub 保留完整历史；正式发布、定时补偿和手动执行都遵循此规则，不会因旧版编辑事件重新上传过期附件。同步仍清点全部目标附件及预留容量，并在清理前校验 GitHub 历史原件与 Gitee 副本的大小和 SHA-256。源码、标签、已有发布记录和目标独有文件不删除。具体分阶段清理及恢复规则见 [GitHub 与 Gitee 同步](GitHub-Gitee同步.md)。

若未发布版本仅因云端打包环境失败，可修复主分支的工作流后手动运行 `Release bundles`，传入已存在的 `release_tag`。预检把标签解析为一个固定提交，六个平台和发布器均检出这一提交，并在上传和公开前再次验证远端标签；不移动标签、不将主分支的新代码混入旧标签安装包。Linux AppImage 打包机必须安装提供 `xdg-open` 的 `xdg-utils`。同步工作流的 `release_tag` 不会覆盖最新版保留规则；手动执行默认 `dry_run=true`，先核对清单，再设为 `false` 执行实际同步和清理。

macOS 更新包会将 `RouteDeck.app.tar.gz` 重命名为含版本与架构的唯一文件名；不改变文件内容。Windows 清单同时提供 NSIS/MSI，Linux 提供 AppImage。更新包大小上限 256 MiB；Gitee 原有附件大小、总容量和权限限制仍生效，超额不能通过忽略文件解决。

## 本地安装与正式发版一致

本地 `tauri build` 产物是候选包，不是 CI 正式包的替代物。正式发版完成后，从所选官方 Release 下载对应安装包和 `.sig`，对照 `SHA256SUMS.txt`，并执行：

```powershell
node scripts/verify-update-signature.mjs src-tauri/tauri.conf.json <安装包绝对路径> <签名绝对路径>
```

确认安装时机再运行该正式包；旧版 0.6.x 需要此一次性手动升级。后续通过软件内更新获取的也是正式发布包，不会在用户电脑上重建。

安装后可只读核对 Windows 文件版本：

```powershell
pwsh -File scripts/verify-local-version.ps1 -PublishedVersion 0.7.1
```

这个核对脚本不安装、不停止进程，也不调整代理；返回不一致时不能宣称“已同步”。版本一致不代表本地候选包与 CI 包逐字节一致，所以首次升级必须使用通过摘要与签名验证的正式安装包。

## 安全边界与验收

- 只接受固定官方仓库的 HTTPS 下载地址，严格绑定版本、架构、大小和摘要；前端不能传入任意路径、下载地址或安装内容。
- 原生层阻止并发检查/下载/安装、陈旧版本安装及降级。任何签名或摘要失败均不进入安装就绪状态。
- 未启用 updater 的 reqwest system-proxy 功能，避免依赖特性合并改变其他本地控制请求的路由。
- 离线测试和浏览器合成验收不等于真实升级验收。上线前在测试设备上从上一正式版完成升级，核对 NSIS/MSI、macOS、AppImage 分别的安装/重启、数据保留和失败恢复。不要在用户的活动代理或 Codex 会话上自动做此测试。
