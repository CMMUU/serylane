# 发布上传故障恢复

仅处理已完成六平台构建与安装验收、但 GitHub 附件上传失败的情况，不是跳过发布检查的快捷入口。

1. 先确认原 `Release bundles` 已停止，六个 `bundle` 成功，六份原始产物未过期，固定版本标签仍指向原构建提交。禁止覆盖标签、重签名或混入新构建。
2. 用发布附件列表检查不确定的上传。完整 `uploaded` 附件不得删除或替换；只有确认原上传任务停止、仍未完成且不能下载的草稿 `starter` 占位，才能在核对精确发布 ID / 附件 ID / 名称后清理。保留原 CI 产物用于恢复。不自动批量删除。
3. 在可信 `main` 手动运行 `Recover verified release publication`，提供原运行 ID 和已有版本标签。只读检查仓库身份、来源工作流、六平台及 Windows 原生/安装测试、产物归属与标签一致性。恢复过程不重编译，使用原提交的发布器和原签名产物；可选 Mac / Ubuntu GitHub-hosted runner 的 HTTP/1.1 上传连接只用于排除传输故障，不降低 TLS、签名或哈希检查。任何已有内容冲突都会停止。
4. 恢复发布后仍必须执行 `Sync GitHub to Gitee` 全量镜像，并等待其官网部署与线上验证。恢复工作流本身不等于完整交付，未完成国内附件验证和六个官网下载入口验证时，不报告发版完成。

这一流程不安装、启动或更改用户电脑上的应用或代理。工作流维护提交可以晚于应用标签；镜像的 `main` 和官网应对应最新维护提交，安装包与发布标签必须继续对应原构建提交。

上传传输单独使用固定 `uploads.github.com`、校验证书的 HTTP/1.1 连接、明确 Content-Length、30 秒发送空闲超时、5 分钟发送期限和 120 秒服务端确认等待，并记录无敏感数据的字节进度。不跟随重定向、不自动重试不确定的 POST。此适配器仅替换原发布器的上传方法；原发布器的源码洁净、版本、签名、内容冲突及完整附件集检查不变。
