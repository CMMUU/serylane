## 问题与目标

旧的普通关闭路径将当前模式改为 Manual。系统代理关闭后核心继续运行，TUN 关闭后也可能重新启动 Manual 核心；界面继续按核心进程显示运行中，启动按钮不可用。保存模式被覆盖后，下次启动及恢复也可能只开启本地端口。

路由页面使用核心内的域名分流规则，不是旧版独立模型中转。旧状态只核对规则是否加载，没有同时说明系统代理/TUN 入口；核心停止后也可能短暂保留之前的路由高亮。配置开关、核心运行和接管状态不能互相代替。

## 统一的状态矩阵

| 场景 | 主代理显示 | 路由显示 |
| --- | --- | --- |
| 系统代理、TUN 都关闭，路由未启用 | 已关闭 | 已关闭 |
| 系统代理、TUN 都关闭，路由已启用 | 已关闭 | 已启用 · 暂停，等待代理启动 |
| 系统代理或 TUN 开启，路由未启用 | 对应模式运行中 | 已关闭 |
| 代理开启，路由规则和出口核验通过 | 对应模式运行中 | 路由已就绪 · 系统代理／TUN |
| 正在启停、切换或核验失败 | 实际操作或错误 | 正在核验／暂未生效，并说明原因 |

表中关闭指普通主代理停止。显式 Manual 仍允许客户端通过本地 HTTP/SOCKS 端口使用核心，应标明仅本地入口，不能断言没有流量，也不能显示系统代理/TUN 已接管。其他客户端的系统设置不属于本应用的停止范围。

## 意图与实际状态

- 主代理运行意图：`desired_running`。明确关闭时先记录停止，再清理；退出清理与暂时故障不能把用户停止改写成开启。
- 下次启动方式：保存的 `network_mode`。普通关闭不再将其改成 Manual；历史 Manual 可能是明确选择，不能推断并改写成系统代理。
- 路由策略意图：`Document.enabled` 与 `applied`。名单和出口保留，保存草稿与确认应用继续分开。
- 核心与入口：核心运行只证明本地进程可用，系统代理须读回接管，TUN 按实际平台检查。读取失败与明确关闭分别呈现。
- 路由规则核验：`verification` 表示规则核对，`ingress` 说明当前入口。规则载入不能单独证明系统流量已进入，更不能证明外网、登录或模型长流成功。

只在已启用策略、核心可用、规则模式、有效出口及规则核对通过，并确认当前系统代理/TUN 入口时，显示相应路由就绪。错误和未知状态不沿用旧的成功高亮。全局／直连模式明确说明域名路由暂不生效；目标组缺失继续使用既有拒绝规则，不扩大路由范围或静默换出口。

## 操作之间的关系

1. 关闭当前系统代理或 TUN：使用统一停止流程，取消后台恢复，保留模式和路由设置；核心停止后路由进入等待启动。
2. 点击启动：读取最新模式与选用配置，执行既有权限和启动验收，加载已应用路由策略，再核对入口与规则。
3. 主代理关闭时开启路由：只保存启用意图，主代理保持停止；界面明确等待启动。
4. 单独关闭路由：移除该模块的域名规则覆盖，主代理继续原状态，其他本地及订阅规则保持。
5. 开机恢复：主代理停止意图不因路由已启用而自动变为开启；已有开启意图按原模式恢复，路由等待同一核心重新核验。

路由开关继续表示配置意图，当前状态说明就绪、暂停或待核对。不能把等待状态伪装成关闭按钮，再让用户点击时意外取消保存的策略。现有显式确认、配置修订号和所有权保护保留。

## 同步与失败处理

开始启动、停止或切换时使旧路由核验失效；读回应对应当前配置、核心会话和接管入口，迟到结果不得覆盖新状态。操作完成后统一刷新主代理与路由，轮询只用于补充外部变化和异常退出的发现。

托盘等原生停止事务完成后发送 `proxy-stop-finished` 结果通知。界面空闲时立即使旧核验失效并重新读取主代理、路由与恢复状态，不再只等待三秒周期刷新；界面自己的写操作仍由原有最终读回处理。通知中的成功／失败只用于提示核对方向，界面仍读取实际运行和接管状态，失败显示关闭未完成并允许重试。

读取错误显示待核对；停止清理失败显示未完成；切换或应用失败保留原错误与回退结果。读取状态不改变网络、不自动重启核心、不抢占第三方代理。路由编辑内容、启用意图和未应用草稿分别保留，刷新不丢编辑或改变已经确认的策略。
