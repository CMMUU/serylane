# TUN 三端稳定化方案

[文档索引](index.md) · [当前启用与兼容性](TUN启用与兼容性.md)

审计日期：2026-10-30。代码基线：`6364bad8ff7336fbad84168afb2a37675bd359eb`（v0.7.33）。本文区分现有实现、代码审计发现和待实施设计；**不是“三端 TUN 已稳定”的发布声明**。本轮没有安装辅助服务、启动 TUN、改动系统网络或执行实机故障注入。

建议沿用 Mihomo 数据转发能力，统一“普通权限界面 + 有限指令的权限辅助服务 + 会话生命周期”，分别接入 Windows SCM、macOS SMAppService/launchd 和 Linux systemd/polkit。先补齐网络资源归属与恢复，再逐个平台开放稳定版入口。TUN 改变流量接入方式，不能修复节点上游故障，也不能无缝续接已经中断的 ChatGPT 数据流。

## 1. 当前实现与边界

| 项目 | 代码中的当前行为 | 仍缺少的证据或能力 |
| --- | --- | --- |
| Windows | 检查当前进程 TokenElevation；用户需退出后以管理员身份运行整个应用；TUN 核心随应用启动/停止，没有独立 Windows 服务 | 普通权限界面配合特权服务；驱动、DNS、路由、休眠与崩溃的完整实机验收。仍为实验性 |
| macOS | 已有 SMAppService/launchd 辅助服务、签名检查、受认证 XPC、UID 与租约隔离、心跳看门狗 | 正式签名发行链及 Intel/M 系列实机验收；跨 Helper 崩溃的恢复账本。兼容发行包不包含 Developer ID 或公证，不能据此宣称 TUN 可用 |
| Linux | `tun_service` 返回 Unsupported；界面禁用 TUN 选项 | 权限服务、系统网络适配、安装卸载、发行版测试均未实现；不能只解除按钮禁用 |
| 有效配置 | 从订阅移除原始 `tun`，由应用生成 `enable`、`stack: mixed`、`auto-route`、`auto-detect-interface` 和 UDP/TCP 53 的 `dns-hijack` | 没有按平台管理的路由/DNS 所有权清单，没有统一实机验证后的参数档位 |
| 启动验收 | 核心运行状态、近期 TUN/权限/路由错误日志，再做不使用显式 HTTP 代理的 HTTPS 检查 | HTTPS 成功不能单独证明经过 TUN；双站点失败仍会触发 TUN 停止，无法充分区分本地接管失败与外网暂时不可达 |
| 退出与恢复 | 已有会话恢复开关、取消/关闭协调；Windows 子进程 Job Object 及关机门禁；macOS Helper 有心跳租约 | 系统代理恢复账本不能等同于 TUN 路由/DNS 恢复账本；尚无三端一致的网络资源核验与故障恢复报告 |

代码依据：[权限分派](../src-tauri/src/tun_service/mod.rs)、[Windows 提权状态](../src-tauri/src/tun_service/windows.rs)、[macOS Helper](../src-tauri/src/tun_service/daemon.rs)、[有效配置](../src-tauri/src/effective.rs)、[启动流程](../src-tauri/src/lib.rs)、[网络检查](../src-tauri/src/network_safety.rs)、[系统代理事务](../src-tauri/src/platform.rs)、[会话恢复](../src-tauri/src/session_resume.rs)、[Windows 子进程归属](../src-tauri/src/windows_process.rs)。

已实现的 macOS 保护值得保留：协议 v2；配置最多 4 MiB；仅允许固定操作；不允许运行中 prepare/start 覆盖会话；本地 generation 与 Helper 租约共同防止迟到响应停止新会话；根拥有的运行目录；核心签名、普通文件与不安全路径检查。当前看门狗每 2 秒检查、心跳超时阈值为 18 秒；这是代码参数，不是恢复耗时承诺。`stop_child` 当前直接终止子进程并等待，没有独立的持久化 TUN 资源恢复事务。依据：[协议](../src-tauri/src/tun_service/protocol.rs)、[协调](../src-tauri/src/tun_service/lifecycle.rs)、[Helper 实现](../src-tauri/src/tun_service/daemon.rs)。

产品边界保持清楚：TUN 不因阅读设置、保存配置或安装更新自动启用；恢复上次状态须符合现有恢复开关和用户选择。“路由”域名规则不因本方案自动开启；已经关闭的程序代理和旧 Codex 接管能力不因本方案恢复。当前程序代理能力开关见 [capabilities.rs](../src-tauri/src/capabilities.rs)。

## 2. 先处理的四个问题

### 2.1 本地接管和外网健康分别判断

当前 `verify_tun_route` 使用 `no_proxy()`，只是不使用客户端显式代理；它没有验证系统选路确实进入 Serylane 的接口。机器原本能直连时可能产生误判；网站受限或节点暂时失败时，又可能把上游问题当成本地 TUN 启动失败。

改为两组结果：

- **接管验收**：当前租约拥有核心；接口确实存在；IPv4/IPv6 选路与策略一致；核心出站不回流；已设置的 DNS/防火墙状态可读回；控制端认证正常。此类失败阻止“接管成功”，并执行有归属的回滚。
- **网络健康**：基础网站、DNS 解析及应用专项检测。失败显示受影响的层次并保留诊断，不能仅凭一次外网失败清空正常连接或反复重建 TUN。若证据表明本地接管造成持续断网，再进入有界恢复事务。

保留基础联网与 OpenAI 检查分离：现有代码允许 Google/Cloudflare 任一基础目标通过；OpenAI `/v1/models` 的 401 只说明该端点的传输和响应情况，不证明账号、模型请求、WebSocket/SSE 或长流可用。新增功能必须使用受控测试服务证明流量路径，不能把认证失败写成“模型验证成功”。

### 2.2 网络资源有唯一归属

TUN 状态不能只用 PID 或“已运行”表示。每次接管建立事务 ID、租约、用户身份、核心身份、配置摘要、系统启动标识及资源清单。资源包括实际接口标识、路由/策略路由、DNS 修改和防火墙条目。退出只恢复本事务仍拥有的资源。

现有系统代理的快照/租约只覆盖系统代理，不覆盖这些资源。新账本应由权限服务保管，敏感配置与摘要分开，事务准备及提交原子写入。恢复时逐项比较“原值、本应用写入值、现在观察值”，发现其他 VPN、DHCP 或用户改动就停止覆盖并记录冲突；不全局清空路由、防火墙或 DNS。

### 2.3 停止是协议，而不只是 kill

先禁止新启动与配置替换，申请正常退出并等待核心回收，再核验所拥有的资源；超时才由宿主终止本会话进程树，随后尝试定向恢复。正常退出通道须针对固定 Mihomo 版本验证：Unix 信号和 Windows 可用的控制方式不能直接互相类推。

若 Helper 自身崩溃、被强杀或机器断电，应用代码可能没有机会清理。OS 回收非持久接口并不等于所有 DNS、策略路由和防火墙设置均已恢复。重新启动服务/应用时先对账后恢复；无法确认归属时提示异常，不能谎报“已安全恢复”。

### 2.4 权限只用于必要的部分

整个含 WebView 的界面不应长期持有管理员/root 权限。辅助服务必须把界面和其输入当作不可信：仅允许校验、启动、停止当前租约、读取状态和有限日志；拒绝任意命令、可执行文件路径、环境变量注入和任意文件读写。订阅生成的配置仍需在服务端进行独立约束，不能只依赖前端校验。

## 3. 共同架构与接口

```text
普通权限 Serylane 界面与应用状态管理
  │  经过操作系统认证的本地 IPC；固定操作、超时和会话租约
  ▼
平台辅助服务（Windows SCM / macOS launchd / Linux systemd）
  ├─ 调用者授权、协议版本、核心身份和配置白名单
  ├─ 网络资源账本、状态读回、异常恢复
  └─ 拥有当前会话的 Mihomo 进程及必要的网络权限
       └─ TUN / DNS / 选路 / 数据转发
```

这是权限边界设计，不表示 Mihomo 已能完全无特权运行。核心创建接口、管理路由等仍需平台权限；后续如要将接口创建与数据转发进一步拆分，需验证 Mihomo 的受支持接口、句柄传递和升级兼容性，不能先假定可行。

建议把现有 `tun_service` 抽成平台适配接口，复用租约与单飞检查。接口契约包含 `inspect_capabilities`、`prepare`、`start`、`heartbeat`、`stop_lease`、`inspect_owned_network`、`recover_owned_network`。这些新接口均为待实现，协议版本需显式协商，旧服务不能把新指令解释成无条件停止。

状态分为三个维度，不再混用一个“已就绪”：

| 维度 | 示例状态 | 能说明什么 |
| --- | --- | --- |
| 安装/权限 | 未安装、需批准、签名不符、协议不兼容、可用 | 是否有权限执行下一步 |
| 接管会话 | 停止、准备、启动、接管已验证、停止中、需恢复、归属冲突 | 本地核心和网络资源是否一致 |
| 网络健康 | 未测、检查中、可用、部分受限、不可达 | 检测当时相应目标的情况 |

所有变更带 `generation + lease`；启动、停止、更新和恢复串行提交。状态读取只读，不能启动核心、修复授权或改变网络。关闭窗口仍进入托盘；显式“退出”结束本应用代理；权限服务安装后可以待命，但不能据此在无人登录时擅自恢复代理。

## 4. 各平台落地方式

### 4.1 Windows：SCM 服务取代整个界面提权

首次明确安装权限组件时经过 UAC；以后普通权限界面连接固定服务。服务二进制、配置目录和安装目录由管理员控制，普通用户不能替换。服务账户与权限先做驱动/API 最小权限验证：若创建适配器和路由确实需要 LocalSystem，可暂由**独立、受限接口的服务**承担，不能声称换成 LocalService 就一定可用。再收紧 service SID、对象 ACL 和不必要令牌权限。SCM 服务创建与服务访问权限是不同权限，必须分别设置。[Microsoft 服务访问控制](https://learn.microsoft.com/en-us/windows/win32/services/service-security-and-access-rights)

IPC 使用仅本机命名管道、显式 DACL、受授权用户/登录会话身份；拒绝远程连接。不能使用默认管道 ACL，不能仅凭传入 PID 或管道名信任客户端。每次请求核对令牌身份和租约；必要的客户端身份验证以操作系统提供的连接信息为基础，避免 PID 重用和路径替换。客户端也验证服务端，授权失败不会继续执行特权操作。[管道访问控制](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights)、[连接客户端安全上下文](https://learn.microsoft.com/en-us/windows/win32/ipc/impersonating-a-named-pipe-client)

服务拥有核心 Job Object，保留 `KILL_ON_JOB_CLOSE` 兜底，检查驱动架构与依赖。UAC 拒绝、端口/接口冲突、服务停止或驱动失败均保留明确状态。接入 SCM 停止/关机通知并用有限时间做正常清理；仅在确有必要时使用 preshutdown，不无限阻塞系统关机。[服务控制通知](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/nc-winsvc-lphandler_function_ex)

现有管理员会话路径暂留作实验兼容入口，迁移成功且实测通过后再移除。更新需匹配应用、服务协议、Mihomo 与驱动版本；验证后切换，失败保留可回退的上一组文件。首次安装和服务修复是独立操作，不伪装成每次点击“启动”的后台授权。

### 4.2 macOS：补齐现有辅助服务，不绕过签名

优先复用现有 SMAppService/launchd + XPC 方案。当前最低系统版本是 macOS 13；SMAppService 也从 macOS 13 提供对包内辅助程序、LaunchAgent 和 LaunchDaemon 的管理。注册仍受用户批准，系统状态为 enabled 也要经过真实认证握手才能显示就绪。[Apple SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice)

正式可用的前提是受控 Apple Developer 签名身份：主包、辅助程序、登录助手和内嵌核心按发行要求使用一致团队的有效签名；Hardened Runtime、时间戳、公证与 ticket 验证进入流水线。项目更新包签名、ad-hoc 签名和 Developer ID 是不同校验，不能相互替代。凭据应由发行负责人通过受限密钥库/CI secrets 配置，本方案不收集密码、证书私钥或令牌。[Apple 公证要求](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)

保持现有 XPC 指定代码身份和 UID 校验，补持久化网络账本、优雅退出、Helper 重启后对账及休眠/唤醒协调。旧 Helper 注销未完成时禁止覆盖安装；应用更新前确认旧租约结束；新包身份或协议不匹配时保留网络状态并给出修复原因。安装在临时位置、移动应用包、两个同名应用、用户切换、批准被撤销均要有测试。

NetworkExtension/Packet Tunnel 是可评估的后续路线，不是给现有 Mihomo 加一个开关。需要验证数据包桥接、生命周期、路由/DNS 能力、资源与签名配置；站外发行需要相应 capability、provisioning profile 和 entitlement，不能假定当前账号或包已有。[Apple Network Extensions entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.networking.networkextension)

首阶段不切换到 NetworkExtension、不安装根证书、不解密 TLS；TUN 与应用流量检测均不需要中间人代理。

### 4.3 Linux：先限定支持范围，再启用入口

首个目标是有 systemd、polkit 和图形会话授权代理的桌面环境；以明确的发行版/版本清单发布，不承诺“所有 Linux”。先准备原生安装包安装 root 拥有的服务、策略和二进制；AppImage 继续作为普通权限界面载体。仅更新 AppImage 不能等同于已更新系统权限组件，须进行服务协议兼容检查。

服务通过 system bus 或受保护 Unix socket 识别调用者，每次特权操作经窄范围 polkit action 决策；只授权本应用操作，不给任意 `systemctl`、shell 或文件路径执行权。缺少会话授权代理时提示安装条件并保持禁用，不回退为免密码 sudo 或 setuid GUI。[polkit 机制与逐请求授权](https://www.freedesktop.org/software/polkit/docs/latest/polkit.8.html)

权限从 `/dev/net/tun` 和 `CAP_NET_ADMIN` 的实际需求出发；是否还需 `CAP_NET_RAW` 等由固定核心/配置实测决定，不默认授予 `CAP_SYS_ADMIN` 或全部能力。系统单元限制 capability、可写目录、设备及可执行路径；`NoNewPrivileges` 等设置逐项回归。不能机械套用 `PrivateNetwork` 导致接管只作用于隔离命名空间，也不能用未适配的设备隔离隐藏 `/dev/net/tun`。[Linux TUN 设备要求](https://docs.kernel.org/networking/tuntap.html)、[systemd 执行环境](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html)

核心与辅助进程留在服务 cgroup，使用正常停止、限时等待及整组终止；禁止 `KillMode=process/none` 造成后台遗留。故障重启有次数/退避限制，重启前完成旧资源对账，不因服务自动重启直接重建用户未请求的代理会话。[systemd 进程终止语义](https://www.freedesktop.org/software/systemd/man/latest/systemd.kill.html)

DNS 分别适配 NetworkManager/systemd-resolved 等已选支持组合，优先使用管理器接口；不把所有机器当成可直接覆盖 `/etc/resolv.conf`。nftables/iptables、策略路由索引、容器网络和其他 VPN 必须检测冲突。完成这些能力与实机门禁之前，Linux TUN 继续禁用。

## 5. 路由、DNS 与数据面

固定核心仍为 [core-manifest.json](../src-tauri/core-manifest.json) 中的 Mihomo v1.19.30。上游文档会更新，不能把最新示例中的栈名或 `dns-mode` 等字段直接写进当前包；每个新增参数须对照固定版本源码、原生配置校验和实际效果验证。[固定版本配置源码](https://github.com/MetaCubeX/mihomo/blob/v1.19.30/config/config.go)

候选策略如下，**均非本轮已修改的默认配置**：

| 事项 | 建议 |
| --- | --- |
| TCP/UDP 栈 | 以当前 `mixed` 为基线；`system`/其他栈只在同版本平台对比验收后进入兼容档位，不以测速结果单独决定 |
| 自动选网卡 | 常规单出口自动检测；多出口、公司 VPN、虚拟网卡环境记录实际出口并验证，错误时提示选择/冲突，不反复猜测 |
| DNS | 分开记录系统 DNS、TUN 劫持和核心解析结果；保留局域网/企业域名要求；明确验证 IPv6 与加密 DNS 路径，不能宣称拦截所有 DNS |
| strict-route | 只在平台验收后决定默认值；Windows 的防 DNS 泄漏效果与虚拟机兼容性分别验证，开启/关闭均显示真实能力边界 |
| Linux auto-redirect | 作为 Linux 专项候选；先验证 nftables/iptables 版本、冲突和回收，不推广为三端通用开关 |
| MTU/IPv6 | 默认保留经验证基线；用大包、QUIC、双栈/单栈实测定位问题，不能用一刀切关闭 IPv6 掩盖故障 |
| 回环与直连 | 本地控制/代理端口、核心出站、下载中心和局域网依实际规则验收；不因错误路由把核心流量再次送回自己 |

上述平台差异来自上游：`auto-redirect` 为 Linux 专项；多出口自动识别有边界；Windows `strict-route` 涉及 DNS 防护且可能影响虚拟化应用；macOS/Windows 对局域网 DNS 劫持也存在限制。具体行为仍以所打包版本为准。[Mihomo TUN 参数说明](https://wiki.metacubex.one/en/config/inbound/tun/)

代理域名规则、手动节点选择和 OpenAI 稳定策略继续由现有有效配置流程生成。更换节点主要影响后续连接；不能通过周期性清空所有连接来“提高稳定”。规则更新若必须重启核心，须在界面说明会中断连接，并避免后台自动执行。

## 6. 生命周期与恢复矩阵

| 触发事件 | 待实现的处理合同 | 不可承诺的边界 |
| --- | --- | --- |
| 保存设置/查看状态 | 仅保存或读取；不启动、提权、修复服务、切模式 | 保存成功不等于接管成功 |
| 明确启动 TUN | 核对权限和冲突 → 准备账本 → 启动 → 读回本地资源 → 提交 → 异步健康检测 | 网站成功不是接管证据 |
| 关闭窗口 | 普通权限应用留托盘，继续持有当前租约 | 不等于退出应用 |
| 明确停止/退出 | 取消重试与恢复任务，阻止新进程；正常停止并核验；仅回收当前资源 | 不关闭用户其他代理/VPN |
| GUI 崩溃/被结束 | Helper 依据租约失效收束当前会话；宿主负责进程树兜底 | 当前看门狗阈值不是立即恢复保证；Helper 同时失效另走恢复路径 |
| Helper 崩溃/强杀 | OS 管理器回收/监管子进程；重启先核对资源账本、身份与当前系统状态 | SIGKILL/断电无法执行用户态清理；不能保证当下零残留 |
| 系统关机/重启 | 分开记录“用户希望下次运行”与“当前资源已释放”；限时清理 | 不无限阻塞关机，不把正常关机误写成用户主动停止 |
| 登录恢复 | 只在用户启用登录启动、恢复上次运行且权限仍有效时恢复相同模式；静默则仅托盘 | 未授权/需重新批准时暂停，不能自动弹终端或降级切模式 |
| 休眠/唤醒 | 接入 OS 电源事件；协调租约，唤醒后重新确认出口和资源；有界恢复 | 增大心跳超时不是完整方案；原 TCP/模型流可能已失效 |
| Wi-Fi/有线/热点切换 | 防抖处理网络变化，核对接口与路由；能保持会话则保持，否则说明重建原因 | 不按固定周期重启，不覆盖新 DHCP/DNS 或其他 VPN 的改动 |
| 安装更新/服务修复 | 单独确认后停旧租约、验证新组件身份与协议、切换并读回；失败可回退 | 下载和检查更新不停止代理；不能后台替换运行中的特权核心 |

默认恢复目标是撤销本应用接管并尽可能恢复原网络状态；“代理不可用就阻断所有流量”的 kill switch 是另一项产品策略，当前不作为已有功能承诺，也不能通过遗留黑洞路由意外实现。

## 7. 用户可见状态与诊断

首页和设置统一显示当前实际模式、服务权限、核心运行、TUN 接管、网络健康，不把“核心进程存在”渲染成“已全面接管”。错误至少区分：缺权限/拒绝授权、包身份、协议不兼容、驱动或设备、端口、配置、接口/路由冲突、DNS、上游连接、恢复不完整。

日志使用现有应用日志保留设置（默认 3 天），新增结构化阶段、错误码、会话关联 ID、耗时、平台/核心版本和恢复结果。敏感配置、订阅 URL、认证令牌、聊天内容、请求正文、完整命令行不入日志；诊断导出须明确范围并脱敏。特权服务的系统日志也需限量，避免 GUI 日志保留设置被系统级日志绕开。正式“恢复完成”必须有资源读回结果支撑。

恢复按钮只处理能证明归属的资源；检测到冲突时展示具体原因和当前观察状态，不能提供“全局重置网络”作为默认操作。

## 8. 测试矩阵和发布门禁

以下是计划验收项，不是已完成测试记录。每次记录 OS/架构、安装包及核心摘要、服务协议、网络环境、预期/实际结果、失败日志；未覆盖环境明确标注。

| 层次 | 必须覆盖 |
| --- | --- |
| 纯逻辑/模拟 | 状态机、所有权比较、资源账本损坏/中断、重复启动、迟到心跳、租约替换、网络事件乱序、停止/更新/恢复竞态 |
| IPC 安全 | 未授权用户、其他登录会话、假服务端、协议降级、超大/错误消息、路径和符号链接注入、被替换核心、非法配置、请求超时 |
| 打包/安装 | Windows x64/ARM64；macOS Intel/Apple Silicon；Linux x64/ARM64。干净安装、拒绝授权、旧版升级、回滚、卸载、移动/重复包、损坏包 |
| 网络 | IPv4/IPv6/双栈、UDP/TCP DNS、DoH、局域网设备、多个出口、代理节点不可达、门户认证、企业 VPN/虚拟机/容器、防火墙拦截 |
| 生命周期 | 连续启停、退出、GUI/核心/Helper 分别异常退出、服务重启、系统重启、取消关机、睡眠/休眠/唤醒、热点/有线/Wi-Fi 切换 |
| 应用 | 浏览器 HTTPS、下载/大文件、QUIC/UDP、WebSocket/SSE、ChatGPT/Codex 长流；区分受控服务结果与真实业务结果 |
| 恢复 | 启停前后路由/DNS/防火墙逐项对照；运行中外部 VPN/DHCP/用户改动；未取得归属时不得覆盖；异常后再次启动可诊断 |

可重复的最低门禁：

1. 每个平台候选版本通过逻辑/IPC 测试与对应架构构建；缺权限和未授权请求不得改变网络。
2. 安装包、服务与核心身份验证通过；macOS 缺 Developer ID/公证时只能标记兼容包，不能开放为稳定 TUN。
3. 在声明支持的真实系统中，受控流量能证明进入目标 TUN，核心出站无回环；IPv4/IPv6/DNS 的声明与实测一致。
4. 正常停止无本应用网络资源遗留；异常路径可恢复或明确报告未恢复，不误删外部资源；重复操作与旧会话响应不影响新会话。
5. 受控长连接测试中，本应用不因定时测速或无关目标失败主动断开健康连接；真实上游中断记录原因，不能归类为已解决。
6. 同平台上一个正式版与候选版做同环境对比，记录启动/恢复耗时、故障次数及资源占用，再确定可接受阈值。没有测量前不填写“提升百分比”“零断线”或“所有场景稳定”。

耗时预算、长流持续时间、重复轮数和资源上限须在执行测试前写入测试记录并固定；失败后不能临时放宽阈值来宣称通过。破坏性故障注入只在隔离设备/虚拟机执行，带外保留恢复途径；不能在用户正在使用的主机上模拟强杀或重启。

## 9. 分阶段交付

| 阶段 | 交付物 | 完成条件 |
| --- | --- | --- |
| A：共同基线 | 服务能力合同、接管/健康分离、网络资源账本、模拟适配器和状态机测试 | 纯逻辑/竞态/错误分类可重复验证；不扩大现有平台支持声明 |
| B：Windows 服务 | SCM、认证管道、固定核心与驱动、安装卸载迁移、恢复适配器 | 两种架构的驱动及实际网络/关机验收；GUI 无需长期提权 |
| C：macOS 正式发行 | 配齐发行签名公证、扩展现有 Helper 恢复/退出协议、升级回滚 | Intel/M 系列新装与升级、认证握手、真实接管、唤醒/网络切换验收 |
| D：Linux 首批支持 | 明确发行版列表、systemd/polkit、原生权限组件包、DNS/路由适配器 | 两种架构及选定桌面组合通过后再启用 TUN，其他环境明确不支持 |
| E：稳定版开放 | 回归记录、已知限制、诊断说明、官网与文档能力表 | 按平台独立通过门禁再取消实验标签，不以六平台打包成功替代实机验收 |

阶段 B/C/D 可以在共同协议稳定后并行开发；其中 macOS 需要有效签名身份与 Mac 实机，Linux 需要确定首批发行版/桌面和服务包分发方式，Windows 需要管理员隔离测试机及 ARM64 设备/兼容验证条件。这些是实施依赖，本文不宣称已经具备，也不以索取聊天中的凭据解决。

后续可拓展：更细的多出口策略、显式 kill switch、macOS NetworkExtension、经过实测的参数档位、跨平台统一恢复报告。每项分别定义授权、故障模式和验收，不与本轮基本 TUN 稳定化一起默认开启。
