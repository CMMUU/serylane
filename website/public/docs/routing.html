Serylane / Docs / Domain routing

Route by domain, without changing who controls your network.

Optional domain rules send matching AI-tool connections to an exit policy group in your current subscription. Routing is off by default, applies inside the proxy core, and does not add Codex attachment.

The website’s product illustration is read-only, not live traffic. Browsing this guide does not contact your local proxy, launch an app or change your configuration. Client labels may remain Chinese; this English guide does not imply an English app interface.

Tool presets and custom domains

Choose OpenAI (ChatGPT / API), Claude, and Gemini (including AI Studio / API). A new draft selects only OpenAI; this does not enable routing. The backend expands tool domains, validates and deduplicates them with custom entries, and exposes each tool’s scope for inspection. Removing a tool does not delete your custom entries.

Tool lists may change by version. Already-applied rules keep their saved snapshot; a new list does not replace live rules until you save and explicitly apply it again.

Custom entries accept openai.com, *.openai.com or a form such as https://*.openai.com/*. A wildcard matches subdomains only: list the root domain separately. Matching covers all HTTPS/WSS paths for a domain; it does not split encrypted URL paths or decrypt TLS.

Shared login, payment and support services, Google-wide public resources and voice IP ranges are not automatically included wholesale. Add a specific required domain deliberately instead.

Saving is not applying

  1. Select tools, add custom domains and explicitly choose an exit policy group from the current subscription. The app does not choose one for you.
  2. Save the draft with 「保存草稿」. Existing traffic rules stay unchanged.
  3. While routing is off, use either routing control and confirm enabling. While it is on, confirm 「应用更改」 (apply changes) to replace the applied draft. Domain-routing rules take precedence over local rules, AI rules and subscription rules; unmatched traffic keeps its original rules.

Only connections already entering the core are affected, and only in rule mode. A stopped core, global mode or direct mode has an explicit inactive reason. If a subscription change removes the target group, matching traffic is rejected rather than silently sent direct: choose a valid exit or turn off domain routing.

Disabling this module removes its override rules, not other rules. Saving, enabling or disabling routing does not start the core, switch system proxy/TUN or change the main proxy’s restoration intent.

Two controls, one routing state

The top-level routing button next to system proxy/TUN and the routing page’s enable/disable control share the same switch and operation lock. The page also offers a status refresh. System proxy and TUN are mutually exclusive takeover modes; domain routing can accompany either without switching between them.

Tool choices are compact, with domain scope and instructions expanded on demand. The original release record introduced the two controls in v0.7.27; it did not add Codex attachment.

Check actual readiness, not just a successful save

Missing exit selection or unsaved edits guide you to the necessary action rather than silently choosing an exit. Returning edits to their saved values allows enabling again. The configuration guidance was introduced in v0.7.29; downloadable availability still depends on the center’s formal package record.

After application, the app checks the core’s mode, total rule count and leading domain rules. From v0.7.36, loaded rules are distinguished from traffic ingress: routing is ready for system proxy or TUN only when that actual entry point is confirmed. Manual is labeled as a local proxy entry only.

A waiting core, invalid exit, mismatched rules and failed state read have different explanations. Refresh or reapply after an abnormal check. Failed application retains your edits; rollback is checked too. A successful submission alone is not proof of an effective route.

Stopping the proxy retains routing configuration

The switch records whether this policy is enabled; status describes whether it can work now. Turning off system proxy or TUN uses the main stop operation and retains the last mode. An enabled route pauses, then is checked again on the next explicit proxy start. Restarting the application after stopping the main proxy does not start it merely because routes exist.

  • Main proxy stopped, routing disabled: both are off.
  • Main proxy stopped, routing enabled: the main proxy is off; routing is enabled but paused, waiting for proxy startup.
  • System proxy or TUN running, routing disabled: the main proxy shows its mode; routing is off.
  • Proxy running with rules and ingress verified: routing is ready and names the confirmed system-proxy or TUN entry.
  • During start, stop, switching or a failed check: status shows verification or a specific inactive reason, never a stale success highlight.

Manual mode may still provide a local port for explicitly configured apps; that is not system proxy or TUN takeover. Global network rates are network-interface statistics, not evidence that domain routing is enabled.

OpenAI recommendations and future-connection failover

Re-screen candidates under 「AI 代理 → OpenAI 自动灾备」 (AI proxy → OpenAI failover) to obtain a recommendation order. The actual selected exit is displayed separately. Two light probe rounds check the ChatGPT website and OpenAI API. Scoring considers connection behavior, multipliers and latency; real-stream outcomes require attributable samples. Ordinary system-proxy tasks remain marked as pending verification.

A healthy current node stays in use. Once a failure is confirmed, rankings guide the exit for subsequent new connections; failed nodes enter cooldown, and manual selection remains available. Cost mode filters unknown multipliers and those above the configured limit. One qualified node is enough to use the feature, but at least two are needed for a backup. Subscription recommendations are for manual choice and do not replace the current subscription’s rules.

The v0.7.39 record describes parallel confirmation of the current and backup paths after an explicit probe failure. A verified exit is selected for future connections once failure is confirmed. 30 seconds is a field-acceptance target, not a measured performance promise; actual results require isolated fault experiments.

Old screening results retain basic Fallback until re-screened. Program proxy, the old enhanced-stability strategy and new Codex attachment remain disabled. This recommendation flow does not promise seamless stream recovery.

Restore old attachment records; do not create new ones

The old model relay does not accept new attachments or restart automatically. Existing Serylane attachment records may restore the original configuration only after ownership checks. If an external program changed the same field, backups are kept and the conflict is shown; only legacy restoration remains available.

Old settings files are retained. Old enabled states and concrete paths are not silently converted into domain-routing settings. This recovery path is not a new Codex integration.

What successful checks do not establish

Node changes affect future connections. They do not replay model requests or seamlessly resume a disconnected stream. HTTP 401 can establish API reachability, not a usable account or a verified model session.

Routing does not expand TUN platform support: Windows TUN remains experimental and requires an administrator session; current macOS compatibility packages are not TUN-ready; Linux TUN takeover is not implemented. Review platform boundaries.

Where preset domain scope comes from

First-party domain grouping references OpenAI’s network guidance, Claude’s service-domain guidance and Gemini API documentation. Presets are Serylane routing choices, not a vendor guarantee of complete service availability.
