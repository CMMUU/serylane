Verify the file, then understand the signature.

Check the download center, release, operating system and architecture before installing. SHA-256 establishes file consistency; the project update signature verifies a package against the project’s signing key. Neither is a substitute for operating-system code signing.

Start at the download center

Use the official download section to select the matching system and architecture. Installers are supplied only by the download center; original asset filenames, signatures and hashes remain unchanged. The center’s actual formal-release record—not a source tag—determines what has been published.

If the center is unavailable, the matching package is missing or a check fails, retry later. Do not switch to a GitHub/Gitee download or another architecture or older version. Similar filenames and third-party repackaging do not establish a trustworthy source.

macOS packages distinguish Intel (x64) from Apple silicon (M series, ARM64). See all six system/architecture routes. A browser handoff is not a report that a file has finished downloading.

Compare SHA-256 for the exact filename

  1. Obtain the installer and the project-provided SHA256SUMS.txt from the same version’s formal release record in the download center.
  2. Calculate the installer’s SHA-256. Find the exact same filename in the checksum file and compare the entire digest.
  3. Do not install if they differ. Obtain the file again through the verified center entry. SHA-256 alone does not establish the publisher’s identity; the checksum file must also come from a trusted source.

Windows PowerShell

Get-FileHash -LiteralPath 'C:\Downloads\actual-installer.exe' -Algorithm SHA256

macOS

shasum -a 256 '/Downloads/actual-installer.dmg'

Linux

sha256sum '/Downloads/actual-installer.AppImage'

Replace the example paths with your actual downloaded file. These commands read the file; they do not install or run it. The placeholder filenames are not published asset names.

Project update signatures

The client’s updater checks the project signature on an update package. If signature or integrity checks fail, stop installation and retain the error. For manual inspection, use the signature files and update manifest actually supplied for that same version in the download center.

Independent review can use the source update-signature verification script and the configured public key at the matching release tag. Use the script and key corresponding to the release; do not accept a replacement key from an unknown source. GitHub is a source-review link, not an alternate installer source.

Project signatures are not OS trust approval

A project update signature is not Windows Authenticode, Apple Developer ID or Apple notarization. Do not assume these have been completed without explicit release evidence, and do not automatically bypass operating-system security warnings.

Content integrity, the project’s update signing identity, OS signing and TUN authorization are separate checks. A package can pass the project update check without satisfying macOS TUN helper requirements.

macOS compatibility packages are not TUN-ready

The current compatibility packages retain project update signatures and integrity checks, but do not include the required Developer ID identity or Apple notarization. TUN is not ready in those packages. Reauthorizing a helper or downloading the same temporarily signed package again does not add the missing identity.

Helper-registration repair and a package-signing problem are different conditions. A request to re-associate a service concerns its registration/start state; it does not repair an unsuitable package. A request for a corrected installer requires an actually published package that meets those requirements—not repeated authorization. Stop the proxy before an applicable helper repair, and follow the actual release’s instructions.

Formal signing, notarization and real-device TUN acceptance remain separate work. Review all platform limits; historical v0.7.18/v0.7.19 messages are preserved below.

If an update download is interrupted

The current source flow uses bounded retry, a no-progress timeout and limited recovery of the same download-center file. The interface distinguishes the center, actual network path and attempt. Waiting to retry remains cancellable while the current proxy keeps running. Installation is offered only after signature, size and SHA-256 checks all pass.

A retry keeps the selected version, architecture and content identity; a change in “latest” must not silently select another release. There is no fallback source. Network, certificate, file-verification and installation failures are separate, and old history is not evidence of this attempt’s result.

An old installed version still uses its own updater. If it cannot update, use the official download section for a verified full package of the same architecture, keeping the configuration directory. Source behavior is not a claim that the current installed binary already contains it.

If installation fails

Keep the failure phase and the sanitized error. Check free space, destination permissions, rollback state and proxy state instead of repeatedly clicking install. Preflight happens before stopping the proxy; a failure during replacement needs a different recovery decision from a failed preflight.

In the source fixes documented below, a verified package can be retained during the same run for retry after correcting space or permissions, and the old application backup is retained until the new process confirms the expected version. Do not solve failures by bypassing signature, size or hash checks.

For an older broken built-in updater, obtain an actually published, corrected full installer from the download center, quit the old app, replace it at the same location and keep its configuration directory. Confirm the matching release and architecture rather than assuming a source fix is available as an installer.

Historical signing and installation notes

These versioned records explain earlier behavior and fixes. They are not a claim that a source version is the latest public installer, or that macOS compatibility packages became TUN-ready.

v0.7.28 — Update preflight identity

This source fix separated operating-system names from OS-plus-architecture identifiers to avoid falsely rejecting verified packages. Completion required a new process confirming the expected version. Windows NSIS/MSI checks were distinct; Linux deb/rpm continued through their package managers.

Read the full historical record in Chinese.

v0.7.26 — macOS application-bundle installation

The source fix recognized macOS application bundles correctly and checked completeness, identity and version after backup and replacement. Preflight failure did not stop the proxy. Old backups remained until new-version startup confirmation; rollback, project signing, Developer ID and TUN authorization remained independent.

Read the full historical record in Chinese.

v0.7.24–v0.7.27 — An old updater cannot fix itself before replacement

If built-in installation failed in these versions, the original guidance was a full, actually published v0.7.28-or-later corrected installer from the center, after quitting the old app and retaining configuration. Redownloading the same update or reinstalling v0.7.27 did not replace that old updater logic. Availability still depended on real center attachments.

Read the full historical record in Chinese.

v0.7.18 — Helper state distinctions

The record distinguished helper re-association from a package requiring corrected signing/content. Repeated authorization did not repair missing Developer ID identity, and a project update signature was separate from Apple signing/notarization.

Read the full historical record in Chinese.

v0.7.19 — Compatibility package boundary

Subscription cards, imports, configuration synchronization and custom nodes were delivered first. macOS compatibility packages retained project signatures and integrity checks but not Developer ID or Apple notarization; macOS TUN remained unready and required separate real-device acceptance.
